## Objetivo

Restaurar la Capa 5 (sandbox de SISTEMA OPERATIVO) para ejecutar opencode
aislado del host usando Docker, tras el crash documentado del runtime Bun de
opencode dentro de los user namespaces de bubblewrap en este kernel
(README.md:50, docs/PRUEBAS.md:554). El contenedor ejecuta opencode con el
filesystem del host en SOLO LECTURA salvo el workspace y las rutas de
config/datos de opencode, sin red por defecto, sin capabilities y sin
privilegios, de forma que un fallo del matcher de permisos o del modelo no
puede dañar la maquina anfitriona.

## Criterios de aceptación

- `Containerfile.opencode` construye una imagen reproducible (version fija y
  procedencia documentada, P0.18) con Bun y opencode-ai instalado.
- `scripts/opencode-docker.sh` acepta `[--net] [comando...]` (por defecto
  `opencode`) con la misma interfaz que `scripts/opencode-sandbox.sh`.
- `opencode --version` arranca dentro del contenedor con `--network none`.
- El filesystem raiz del contenedor es de solo lectura: `touch /x` falla.
- Sin `--net` no hay conectividad (DNS/salida fallan); con `--net` si la hay.
- El contenedor corre con `--cap-drop ALL` y `--security-opt no-new-privileges`.
- El workspace se monta de solo lectura; las rutas de datos de opencode
  (`~/.local/share/opencode`, `~/.config/opencode`, `~/.cache/opencode`) se
  montan de lectura/escritura solo si existen en el host.
- Si docker no existe o el daemon no responde, el script falla con mensaje
  claro (fail fast, sin fallbacks silenciosos, P1.19/P1.26).
